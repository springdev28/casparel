01 — What Schoolar Is

A discovery-first library for students and teachers

Schoolar is a full-stack productivity platform for finding, reviewing and organising learning resources — wrapped around class management, schedules, and Google Classroom / Calendar sync.

The landing experience is its smartest decision: an anonymous visitor lands directly on a working resource search — a full-width query bar with filters for source, language, format, subject, grade, rating and sort order, plus a built-in citation maker. There is no marketing wall; you can “Browse resources without an account.” For a discovery product, letting people feel the core value before signing up is exactly right.

Behind the login sits a substantial application. The client bundle reveals roughly two dozen distinct areas — Resources, Classes, Class detail, Lists, Schedule, Goals, Adaptive dashboard, People, Messages, Forum, Canvas, Study sessions, Activities, Profiles, Settings, a Tutorial and an Admin panel — with optional AI-assisted resource discovery and full localisation in six languages (English, Spanish, French, German, Portuguese, Turkish). This is a mature scope, not a prototype.

First-rate delivery, a heavier-than-needed first byte-load

Strength

Delivery infrastructure is excellent

Served over HTTP/2 with Brotli, a ~340 ms time-to-first-byte from an edge cache, hashed assets marked public, max-age=31536000, immutable, and the HTML shell correctly set to no-cache. Returning visitors re-download almost nothing. Code-splitting is real and granular — each page is a lazy chunk.

Strength

Graceful failure when a chunk won’t load

When a lazy chunk fails to fetch, the app shows a clean “Schoolar could not load — Reload app” boundary rather than a white screen. Good resilience engineering.

Medium

The first visit front-loads ~500 KB of JavaScript across ~29 files

Even the anonymous landing page pulls a 417 KB (155 KB compressed) entry bundle plus ~28 further chunks before it is interactive. On a mid-tier phone or slow connection that is a real delay. Split vendor libraries from the app entry, and defer anything not needed to render the search box.

Medium

Over-fragmented chunks — 72 JavaScript files under 2 KB

Icons and tiny helpers are each split into their own hashed file (72 of the ~106 chunks are < 2 KB). HTTP/2 softens the cost, but it still means dozens of round-trips and request overhead. Bundle the icon set and micro-chunks into a small shared vendor file.

Low

Render-blocking web font from a third-party origin

The Space Grotesk stylesheet loads render-blocking from fonts.googleapis.com. preconnect hints soften it, but self-hosting the font (or a font-display:swap fallback) removes an external dependency on the critical path.

Note

Field Core Web Vitals could not be measured here

The audit ran in a sandbox where external fonts were unreachable, which artificially inflated paint timing — so FCP/LCP figures are not reported. The healthy 0.34 s TTFB is encouraging, but a real Lighthouse / CrUX run on production is the recommended next step to confirm interactive timing.

03 — User Experience & Accessibility

Calm, consistent, and friendly — with a few sharp edges

The interface is uncluttered and clearly built on a consistent design system. The gaps are in the details that matter most to first-time and assistive-tech users.

Strength

Low-friction entry & genuine responsiveness

Guest browsing, a “Create one” path from sign-in, labelled auth inputs with helpful example placeholders, and a layout that reflows correctly to mobile. Localisation is offered right at the login screen.

Medium

Search & filter controls lack accessible labels

The seven filter dropdowns and the main search field on the public Resources page expose no <label> or aria-label — a screen reader announces them only as “combobox / edit”. The auth form is done correctly; apply the same treatment here.

Medium

No password recovery, and a weak password floor

The sign-in screen has no “Forgot password?” link, and registration accepts a 6-character minimum with no strength indicator or show/hide toggle. Both are standard expectations for an account-based product handling student data.

Low

Google sign-in is built but not surfaced

The backend exposes /api/auth/google, yet no Google button appears on the login card. Given the Google Classroom / Calendar integrations, one-tap Google auth would cut friction for exactly the target audience.

Low

Small polish items

The “Schoolar” wordmark disappears from the header on mobile; placeholder text doubles as the only label on several filters (it vanishes on focus); and auth screens have no <h1> in the heading hierarchy. None are blocking — all are quick wins.

04 — Discoverability & SEO

The one area that needs urgent attention

A resource-discovery product lives or dies on being found. Right now the configuration works against that — in ways that are invisible in the browser but obvious to a crawler.

Critical

robots.txt blocks Googlebot from the entire site

The live file contains User-agent: Googlebot / Disallow: / while allowing every other crawler. As written, Google will not index a single page. If this is leftover staging config, it is the single highest-priority fix on this list.

High

/sitemap.xml is not a sitemap

Requesting the sitemap returns the SPA’s HTML shell (a “soft” 200), not XML. Search engines get nothing usable. The <meta robots> tag and referenced sitemap imply indexing was intended — the plumbing just isn’t wired up.

Medium

No server rendering — content isn’t in the initial HTML

Every route, including individual resource pages, is rendered entirely client-side; unknown URLs return 200 with the same empty shell (soft-404s). For a catalogue whose value is having its resources found, pre-rendering or SSR of resource and public pages would be transformative for organic reach.

Strength

The metadata itself is well done

Descriptive <title>, meta description, Open Graph and Twitter card tags, and lang="en" are all present and correct. The foundation is there — it just needs to be made reachable.

Note

Two items worth a second look

The auth token is held in localStorage, which is readable by any injected script — an httpOnly cookie is more XSS-resilient (the strict CSP already mitigates much of the risk). And the 6-character password minimum noted above is as much a security concern as a UX one.

In one line: Schoolar is a well-built product wearing an invisibility cloak. The engineering quality is already high; the fastest wins are the two SEO fixes that let the world actually reach it, followed by trimming the first-load payload and closing the accessibility gaps.

Methodology & caveats

Findings are based on headless-Chromium rendering, full network tracing, and direct inspection of production HTTP headers, the JavaScript bundle manifest, robots.txt and /sitemap.xml on 11 Aug 2026. Because the render environment could not reach third-party font origins, paint-timing metrics (FCP/LCP) were unreliable and are deliberately excluded; server-response (TTFB), payload, caching, security and structural findings reflect the live production site. Grades are the reviewer’s qualitative assessment, not a certified score.
